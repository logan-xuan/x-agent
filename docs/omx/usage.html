1. 文档目标

OMX 运行在 Codex CLI 之上，提供的是工作流编排能力， 不是替代执行引擎。对于当前仓库，最有价值的部分是以下四点：

统一入口

把会话启动、状态目录、技能、提示词和本地配置整合到一条路径里。

工作流技能

提供 deep-interview、ralplan、ralph、team 这样的高级工作流指令。

可恢复状态

.omx/ 持久化计划、日志、state、HUD 和团队协作数据。

协作升级

需求澄清、方案确认、持续执行和并行团队可以自然串联，而不是一次次从零开始。

2. 当前环境

关键版本

oh-my-codex v0.12.4
codex-cli 0.119.0
Node.js v23.11.0

项目特点

Python 3.11+、FastAPI、Pydantic v2、SQLAlchemy，重点模块集中在 backend/src/runtime。

健康状态

omx doctor 通过，但 explore 相关 Rust 依赖未就绪，旧技能目录也仍然存在。

当前最重要的环境判断 可以稳定使用 deep-interview / ralplan / ralph / team，但不要把 omx explore 当主入口。

3. 快速开始

最常用的路径只有一条：进入项目目录，然后用高推理强度启动。

推荐启动方式 
cd /Users/xuan.lx/Documents/x-agent
omx --high

强力模式

omx --madmax --high 会绕过审批与沙箱，只在你明确承担风险时使用。

tmux 模式

准备跑 team 时，建议先执行 tmux new -s xagent，再启动 omx。

4. 常用命令

只记住下面这些就够了： omx doctor omx status omx hud --watch omx resume omx session search

状态与诊断

doctor 看安装健康，status 看模式状态，hud --watch 适合在第二个终端盯实时面板。

历史与恢复

resume 恢复交互会话，session search 在本地历史里检索线索。

团队运行时命令 
omx team 3:executor "fix failing tests"
omx team status <team-name>
omx team await <team-name> --timeout-ms 30000 --json
omx team resume <team-name>
omx team shutdown <team-name>
当前实现细节 omx team 现在默认给 worker 配独立 worktree，--worktree 已降级为兼容性保留参数。

5. 推荐工作流

先澄清

$deep-interview 负责明确目标、边界、非目标和决策权限，避免一开始就误解需求。

再规划

$ralplan 负责在实现前做共识规划，让方案、风险、验证路径先收敛。

最后执行

单 owner 持续推进用 $ralph，可拆 lane 的大任务用 $team。

中等任务模板 
$deep-interview --quick "重构 runtime compression pipeline，拆开预算决策与语义裁剪"
$ralplan --interactive "基于澄清后的需求规划实现路径和测试策略"
$ralph "按已批准方案执行并完成验证"
大任务模板 
$deep-interview --standard "澄清 runtime compression redesign 的边界、非目标、验证标准"
$ralplan --interactive --deliberate "产出跨模块的实现计划、风险列表和回归方案"
$team 3:executor "按批准方案并行推进实现、测试和验证"

6. 当前仓库模板

这个仓库的 AGENTS.md 已经写明了单测命令、代码风格和近期重点，因此建议直接把验证门槛写进 prompt，让执行模式不会在“如何算完成”上自由发挥。

Runtime Compression 模板 
$deep-interview --quick "重构 runtime compression redesign，明确 scope、non-goals、回滚策略和验证标准"
$ralplan --interactive --deliberate "基于澄清后的规格，为 backend runtime compression redesign 生成执行计划和验证路径"
$team 3:executor "按已批准计划执行 runtime compression redesign，并以 pytest + ruff 作为完成门槛"
Ralph 验证门槛模板 
$ralph "实现 runtime compression redesign，完成后必须执行：
cd backend &&

pytest --no-cov tests/unit/test_runtime_compression_profiles.py -q &&
ruff check src"

7. 场景建议与详细案例

这一节不只回答“什么时候用哪个命令”，还回答“为什么这样选”。 对当前仓库来说，真正重要的是避免把简单任务做重，或者把复杂任务过早塞进单线程执行。

案例一：单文件、小范围、目标明确的修复

例如某个单测已经指向了具体函数，你只需要修一到两个文件，并把验证跑完。

小范围修复模板 
omx --high
$ralph "修复 runtime compression verifier 的回滚判断，并执行对应单测验证"

适用信号

  • 已经知道要改哪个函数或文件。
  • 成功标准可以直接写成测试或 lint 命令。
  • 任务不需要先澄清边界，也不需要多人并行。

为什么这样选

  • 这类任务的风险不在方向错误，而在遗漏验证。
  • deep-interview 的澄清收益小，额外成本反而更高。
  • team 的 tmux 和 lane 协调对小任务来说属于过度设计。
  • ralph 能把“修复 + 验证”合成一条完成链路。

案例二：需求模糊，用户明确说“不要假设”

例如用户只说“把 runtime compression redesign 做好”，但没有明确边界、非目标和回滚策略。

先澄清再规划模板 
$deep-interview --quick "澄清 runtime compression redesign 的目标、边界、非目标、回滚策略和验证标准"
$ralplan --interactive "基于澄清后的结论规划实现路径和测试策略"

适用信号

  • prompt 里出现“先分析”“先澄清”“不要默认”。
  • 你无法一句话说清楚验收标准。
  • 存在多个互斥方案，但用户还没表态。

为什么这样选

  • 这类任务最怕一开始就沿着错误假设走太远。
  • deep-interview 先明确“要做什么”和“不要做什么”。
  • ralplan 再把澄清结论变成实现顺序和验证路径。
  • 如果直接进入 ralph，未确认的假设很容易混进实现里。

案例三：跨模块改造，但强耦合，优先单 owner 推进

例如要同时改 runtime/context、runtime/turn、gateway，但每一步都依赖前一步的接口和类型收口。

强耦合改造模板 
$deep-interview --quick "明确跨模块改造的 scope、兼容边界和验证标准"
$ralplan --interactive --deliberate "为跨 runtime/gateway 的改造生成顺序化计划"
$ralph "按已批准计划顺序实施，并以 pytest + ruff 作为完成门槛"

适用信号

  • 每一步都依赖上一步的接口或类型变更。
  • 写权限很难切成互不冲突的 2 到 4 份。
  • 实现路径整体偏线性，而不是天然扇出。

为什么这样选

  • 大任务不等于必须并行，强耦合任务并行反而更容易互相覆盖。
  • ralph 更适合顺序推进、持续验证、单 owner 收口的工作。
  • 这里最重要的是降低合并复杂度，而不是追求表面吞吐。

案例四：可以拆 lane 的大任务，优先 team

当任务已经明确，计划也已经批准，并且可以拆成几个相对独立的执行面时，team 的收益会明显高于单线程。

并行团队模板 
$deep-interview --standard "澄清大任务边界、非目标和完成定义"
$ralplan --interactive --deliberate "生成可并行执行的 lane 划分、风险和验证计划"
$team 3:executor "按批准方案并行推进实现、测试和验证"

适用信号

  • 可以清楚写出每个 lane 的文件边界或职责边界。
  • 不同 worker 之间只需要轻量协调。
  • 任务执行时间较长，并且你希望支持中断恢复。

为什么这样选

  • team 的价值不只是“多几个 agent”，而是 tmux、邮箱、共享状态和恢复能力。
  • 测试和验证可以与实现并行，而不是最后集中补。
  • 对跨目录、长执行时间任务，运行时持久化的收益很高。
当前仓库里常见的 lane 切法 lane 1 做 runtime/context 与压缩策略核心实现，lane 2 做 gateway / runtime/turn 适配，lane 3 负责单测补齐、回归验证和 ruff 汇总。

案例五：长任务的监控、恢复和二次进入

如果任务已经跑起来了，你要解决的问题通常不是“怎么开始”，而是“现在进行到哪一步”和“断线后如何接回去”。

监控与恢复模板 
cd /Users/xuan.lx/Documents/x-agent
omx status
omx hud --watch
omx resume
omx team status <team-name>
omx team await <team-name> --timeout-ms 30000 --json

适用信号

  • 你已经有会话或 team 在跑。
  • 你关心的是当前阶段和结果，而不是重新规划。
  • 你需要把执行和观察放在不同终端里。

为什么这样选

  • hud --watch 适合观察，不适合判断“是否启动成功”。
  • 先看 omx status，能避免把 hud: inactive 误判成故障。
  • resume 解决交互会话恢复，team status / await 解决团队运行时视角。

只用 omx --high

目标明确、文件范围明确、不需要并行 worker，也不需要先澄清需求。

优先 deep-interview

需求还很模糊，边界和非目标不清楚，或者不确定哪些决定能自动做。

优先 team

任务能拆 2 到 4 条独立 lane，需要 tmux worker、共享状态和恢复能力。

关于 explore 当前机器更适合把 deep-interview / ralplan / ralph / team 当主路径；omx explore 由于 Rust 依赖未就绪，暂时不要拿它做主要入口。

8. 常见问题

team 启不来

优先检查 tmux -V、echo $TMUX、omx doctor --team。如果不在 tmux 中，体验通常会很差。

技能列表重复

当前机器上旧目录 ~/.agents/skills 还在，虽然是空目录，但可能触发重复显示。

为什么不推荐先用 explore

omx doctor 已提示缺少 Rust 预构建或本地 cargo，因此当前环境不适合把它作为主入口。

最小可用实践是什么

只记三步：cd 项目、omx --high、再按任务规模选择 $deep-interview、$ralplan、$ralph、$team。

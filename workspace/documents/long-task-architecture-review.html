Architecture Review / Long Tasks

长任务编排与分阶段生成架构设计

这份页面将“状态查询打断主任务”和“长报告最终整合阶段超时”两类问题统一收敛为一个完整方案： 主会话只负责下发任务、查询状态和接收结果；worker session 只负责推进主任务；报告生成改为分阶段、分产物、可恢复执行。

主目标：状态查询不再打断主任务
执行模型：Task Registry + Worker Session
产出模型：分阶段生成 + Artifact/Evidence 累积
恢复机制：checkpoint + stage resume

问题定义

问题 1
状态追问打断
用户一句“你在处理吗”进入同一个 session 后，模型当前轮目标会切成“回复状态”，主任务停止推进。
问题 2
最终整合超时
搜集完成后，一次性生成完整长报告/HTML，最终整合 prompt 太重，容易落入 LLM timeout。
系统后果
用户感知为“卡住”
表面看像没继续干活，实质是任务语义和执行路径没有被明确拆开。
关键判断： “长任务”不能再建模成普通聊天消息；“最终报告”也不能再建模成单次大调用的直接输出。

设计原则

  • 长任务必须是独立的任务对象，而不是聊天消息的附属状态。
  • 长任务必须绑定独立 worker session，主会话与 worker 会话彻底隔离。
  • 状态查询必须走旁路，不进入 worker LLM。
  • 最终报告必须分阶段、分章节、分产物生成，不允许单次全量 HTML 大调用。
  • 每个阶段都必须有 checkpoint，可重试、可恢复、可跳过已完成阶段。
  • 主会话只看到三件事：任务已开始、任务当前进展、任务最终结果。

阶段流水线

为什么必须分阶段

  • 避免“搜完资料后一次性生成完整 HTML”导致单次调用过重。
  • 每个阶段都可单独重试，不会因为最后一步超时而丢失全部成果。
  • 用户查询进度时，可以返回具体阶段，而不是笼统地说“还在处理”。
  • 可以把证据切片到具体 section，显著降低 hallucination 和超时风险。
  • 支持阶段级 watchdog、恢复、取消、更新要求。

时间预算、任务级 SLA 与 Watchdog

当前问题
只有步骤级 timeout
单次 LLM、delegate、terminal 各自超时，但系统没有“整个长任务最多允许多久”的统一约束。
目标
双层时限
每个 stage 有自己的 timeout，每个 task 有统一 SLA，再配合 heartbeat 和 watchdog。
用户体感风险
看起来像卡住
某一步超时后没有统一状态机托底，用户只能看到“处理中”，却不知道任务是否仍在推进。

建议时间预算

层级对象建议值说明
步骤级evidence_collect120s工具最密集，通常最慢
步骤级outline_generate60s只看 task + evidence 摘要，不应太重
步骤级section_draft90s / section每个 section 独立限时，不共享一个大 timeout
步骤级document_assemble60s优先合并已有 artifacts，不要再大模型整段重写
任务级interactive_task15 min主会话可随时查进度
任务级deep_research30 min允许多阶段搜集、写作、合并
任务级heavy_batch60 min低交互、长批处理任务

Heartbeat / Watchdog 图

设计要求： 以后必须同时存在“步骤级 timeout”和“任务级 SLA”。 系统不应该只知道“这一步超时了”，还要知道“整个任务接下来该恢复、降级、失败，还是继续”。

需求澄清协议

协议目标

  • worker 可以提出“缺什么信息”，但不能直接与用户对话。
  • owner session 负责把问题展示给用户。
  • 用户回答通过 control queue 回流，不直接进入 worker message history。
  • worker 恢复时读取结构化 answer payload，而不是重新吃整段聊天记录。
核心边界： worker session 可以提问，但不能直接问用户；owner 负责转述，worker 负责继续执行。

关键约束

对象职责绝不能做什么

task control queue 传递结构化 answer / update / cancel 直接持有用户聊天消息历史

agent_core Loop 边界

保留职责

  • 单次 worker 执行回合
  • LLM 调用与工具执行
  • 本轮消息事件流
  • 本轮 `SessionState` 更新
  • 高价值工具结果归档

移出职责

  • 长任务创建与 task_id 生命周期管理
  • owner / worker session 路由
  • 状态查询旁路
  • 澄清请求转发
  • 自动续跑调度
  • watchdog 与 stage 切换
  • 整个任务是否完成的判定

验收标准

交互层

  • 用户连续 10 次问“你在处理吗”，worker 不停止主任务。
  • 状态查询不再触发新的 research 主任务 LLM 调用。
  • 主会话随时能拿到阶段和最近进展，不依赖模型临时总结。

执行层

  • 最终报告不再依赖单次超大调用。
  • 任一 section 失败，不影响其他已完成 section。
  • assemble/render 失败后可从现有 artifacts 恢复。
  • 同一 task 不会跑出多个并发 worker。
最终判断标准： 长任务必须“可持续推进、可中途观测、可阶段恢复、可最终回推”，而不是“用户不追问时才跑，追问时就改口回复状态”。

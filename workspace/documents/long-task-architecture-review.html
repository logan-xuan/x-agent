Architecture Review / Long Tasks

长任务编排与分阶段生成架构设计

这份页面将“状态查询打断主任务”和“长报告最终整合阶段超时”两类问题统一收敛为一个完整方案： 主会话只负责下发任务、查询状态和接收结果；worker session 只负责推进主任务；报告生成改为分阶段、分产物、可恢复执行。

主目标：状态查询不再打断主任务
执行模型：Task Registry + Worker Session
产出模型：分阶段生成 + Artifact/Evidence 累积
恢复机制：checkpoint + stage resume

问题定义

问题 1
状态追问打断
用户一句“你在处理吗”进入同一个 session 后，模型当前轮目标会切成“回复状态”，主任务停止推进。
问题 2
最终整合超时
搜集完成后，一次性生成完整长报告/HTML，最终整合 prompt 太重，容易落入 LLM timeout。
系统后果
用户感知为“卡住”
表面看像没继续干活，实质是任务语义和执行路径没有被明确拆开。
关键判断： “长任务”不能再建模成普通聊天消息；“最终报告”也不能再建模成单次大调用的直接输出。

设计原则

  • 长任务必须是独立的任务对象，而不是聊天消息的附属状态。
  • 长任务必须绑定独立 worker session，主会话与 worker 会话彻底隔离。
  • 状态查询必须走旁路，不进入 worker LLM。
  • 最终报告必须分阶段、分章节、分产物生成，不允许单次全量 HTML 大调用。
  • 每个阶段都必须有 checkpoint，可重试、可恢复、可跳过已完成阶段。
  • 主会话只看到三件事：任务已开始、任务当前进展、任务最终结果。

阶段流水线

为什么必须分阶段

  • 避免“搜完资料后一次性生成完整 HTML”导致单次调用过重。
  • 每个阶段都可单独重试，不会因为最后一步超时而丢失全部成果。
  • 用户查询进度时，可以返回具体阶段，而不是笼统地说“还在处理”。
  • 可以把证据切片到具体 section，显著降低 hallucination 和超时风险。
  • 支持阶段级 watchdog、恢复、取消、更新要求。

任务状态机

状态 含义 进入条件
pending已创建任务，等待执行主会话创建 task
runningworker 正在执行 stageTaskRunner 启动
waiting_input任务需要用户补充输入阶段显式停在缺信息状态
blocked外部依赖阻塞工具、权限、资源不可用
stale超时未更新心跳watchdog 发现无 heartbeat
completed最终结果已产出render/publish 完成
failed任务最终失败超过重试上限或不可恢复错误
cancelled用户取消收到 cancel control

验收标准

交互层

  • 用户连续 10 次问“你在处理吗”，worker 不停止主任务。
  • 状态查询不再触发新的 research 主任务 LLM 调用。
  • 主会话随时能拿到阶段和最近进展，不依赖模型临时总结。

执行层

  • 最终报告不再依赖单次超大调用。
  • 任一 section 失败，不影响其他已完成 section。
  • assemble/render 失败后可从现有 artifacts 恢复。
  • 同一 task 不会跑出多个并发 worker。
最终判断标准： 长任务必须“可持续推进、可中途观测、可阶段恢复、可最终回推”，而不是“用户不追问时才跑，追问时就改口回复状态”。

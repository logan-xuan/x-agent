当前压缩链路

1
Agent Loop
在真正调用 LLM 前，先把对话消息转成 OpenAI 兼容格式，然后进入 ContextAdapter 做压缩准备。
2
Context Adapter
创建 summary_fn，摘要本身也是一次 LLM 调用；同时根据模型参数推导压缩预算。
3
恢复缓存
先从内存缓存取历史压缩结果；如果没有，再从 compression_events 恢复最近一次 compressed_messages。
4
触发判断
只要新增消息数、新增 token 或总 token 超过阈值，就会触发压缩。
5
增量拼装
如果存在缓存，会先把旧的 compressed_messages 与新增消息直接拼起来，再送进压缩器。
6
压缩器处理
默认保留第一条 system 消息，再从后续消息里提取旧摘要，生成增量摘要，并把两者拼接。
7
落库并回填
新的 compressed_messages 会再次写回数据库，下一次恢复缓存时继续作为输入，问题因此会累积。

当前策略拆解

层面 当前实现 优点 隐患
触发条件 新增消息数、新增 token、总 token 任一超阈值即压缩 能尽早拦截长会话 触发频繁，但不校验“压缩是否真的回收预算”
压缩输入 有缓存时直接用 cache.compressed_messages + new_messages 避免从头重算 把旧压缩产物直接二次喂入，容易累积结构性污染
摘要策略 旧摘要 + 新摘要拼接，不做再摘要 看起来保守，避免信息遗漏 摘要会单调增长，最终自己变成主要负担
保留策略 固定保留 50 条 recent messages 近期上下文完整，回复更稳 在 52~55 条消息规模下，几乎没有可压缩空间
缓存恢复 从 DB 直接恢复最近一次 compressed_messages 进程重启后也能延续 如果缓存已坏，问题会跨请求持续放大

发现的问题

历史摘要被误当成原始 system 消息长期保留
High

压缩器先保留第一条 system 消息，再提取后续摘要。对增量压缩来说，第一条 system 往往已经不是“原始系统提示词”， 而是上轮压缩注入的历史摘要。这会导致旧摘要永远保留。

摘要只拼接不再压缩，长度单调增长
High

_merge_summaries() 把旧摘要和新摘要直接拼接，中间只加分隔符。随着会话增长，摘要本身会成为最大 token 消耗项。

固定 retention_count=50 让增量压缩几乎只能处理 3 条消息
Medium

在当前会话里，压缩后的消息数长期维持在 52 左右；下一轮一旦涨到 55，又因为保留 50 条 recent messages，只剩 3 条可归档，算法天然失去回收能力。

缺少压缩质量门槛
Medium

系统会记录压缩事件，但不会检查“本次压缩是否至少回收了 X% token / X 个 token”。因此负收益压缩也会被缓存并继续复用。

建议的改进方向

        

          
            
方向建议预期收益

          
          
            

              消息规范化
              压缩前先剥离所有历史摘要消息，再显式区分“原始 system prompt”和“压缩摘要”。不要用“第一条 system”做隐式推断。
              消除摘要永久驻留问题，避免多份摘要并存。
            

            

              摘要预算治理
              为摘要单独设置 token 上限；超限时对“旧摘要 + 新摘要”做再摘要，而不是继续拼接。
              让摘要长度可控，防止会话后期指数式膨胀。
            

            

              自适应保留窗口
              根据总 token、工具消息密度和摘要长度动态调整 retention_count，而不是固定 50。
              在高压场景下回收更多 token，低压场景下保留更多上下文。
            

            

              质量门槛
              增加压缩收益校验，例如“压缩率必须 > 5% 或净回收至少 1000 tokens”，否则丢弃本次压缩结果，不写回缓存。
              避免把坏的压缩产物继续扩散到后续请求。
            

            

              可观测性
              在日志里同时记录：原始 token、摘要 token、retained token、压缩净收益、收益是否达标。
              更快定位“压缩触发但无收益”的真实原因。
